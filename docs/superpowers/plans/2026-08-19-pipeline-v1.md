# Campaign 4 — Pipeline v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A raw request flows Intake → plan gate (confirm or one reject/revision) → Implement on one pipeline branch → machine Verify → final approval → local merge, with humans only at the two gates.

**Architecture:** Pipeline plans are one-node degenerate DAGs riding the existing workflow engine (`TransparentWorkflow`), so attempts, caps, handoffs, and recovery are reused. New: §4 plan-record fields on `plan_revisions`, a real reject loop, `pipeline_branch`/`base_sha` on work items with cross-stage workspace continuity, a `machine_verify` stage-executor kind wired to campaign 3's `VerifyRunner` via a durable `verify_attempts` table polled by the existing reconciler timer, and a final-approval gate whose approve action performs a hooks-neutralized local merge.

**Tech Stack:** Node 24 / TypeScript, SQLite single-sourced schema (v19 → v20), `node:test` runtime suite, existing collaborator/transaction patterns.

**Spec:** `docs/superpowers/specs/2026-08-19-pipeline-v1-design.md`
(Read it. The exploration findings it cites — file:line seams — are restated per task below.)

## Global Constraints

- **Non-pipeline behavior is untouched.** Multi-node DAG plans, existing lanes, and every pre-existing test pass UNMODIFIED (except where a task explicitly names a test to extend). A pipeline plan is detected as: single node whose stage template is exactly `["implementation", "testing"]` and whose `testing` executor resolves to `machine_verify`.
- **Schema v20 in ONE migration** (Task 1). Later tasks add no schema. Contract stays single-sourced (`src/shared/task-board-contract/index.ts` → SQL CHECKs, validators, web parsers).
- **Forward tolerance:** add optional FIELDS only — never new members of `PLAN_REVISION_STATES`, `WORK_NODE_STATES`, or `WORKFLOW_STAGES` (browser parses those strictly: `validate.ts:905`). New work-item flow uses only existing states (all 13 already shipped in v19).
- **Every work-item state write** goes through `transitionWorkItemInTransaction` (`collaborators/work-item-transitions.ts:79`); every durable write rides `store.transaction` with side effects in `afterCommit`.
- **HTTP conventions** per `service.ts`: regex route + method guard, `readJsonBody` + named parser in `schema.ts` delegating to shared validators, `TaskBoardError` codes from `TASK_BOARD_ERROR_CODES`, human-vs-agent auth per route, `version`/`expectedState` guards for mutations.
- **Git safety:** any git the board or manager runs uses array-args `execFile`, no shell, with `-c core.fsmonitor= -c core.hooksPath=` (campaign 2/3 discipline).
- **No new npm dependencies.** Runtime tests are `node:test` under `tests/`, compiled; `npm run verify:fast -- --base HEAD` is your inner loop; gate = `npm run typecheck:runtime && npm run test:runtime`.
- **Exit codes and reasons are contracts** — copy strings exactly as specified.
- **Spec refinement (recorded):** acceptance criteria stay `string[]` (compat); executable checks land as a NEW optional field `criterionChecks: { criterion: string; check: string }[]` — same §4 intent, no breaking change.
- **Sandbox note (Codex):** loopback only, no Docker. Steps marked **[orchestrator verify]** run later. The controller stages and commits; leave the tree dirty.

### Task 1: Plan-record fields, branch columns, verify_attempts (schema v20)

**Files:** Modify `src/shared/task-board-contract/index.ts`, `validate.ts`; `src/web/task-board/data/parse.ts` (projection only); `src/server/task-board/persistence/store.ts`. Test: `tests/shared/` contract tests + `tests/server/task-board/` migration test (follow the v19 migration test's pattern — find it by grepping `SCHEMA_VERSION` in tests).

**Produces (every later task consumes these exact names):**

```typescript
export const PLAN_CHANGE_SHAPES = ["mechanical_sweep", "feature", "blast_radius"] as const;
export const PLAN_TIERS = ["standard", "hazardous"] as const;
export interface PlanBlockingQuestion { readonly question: string; readonly recommendedDefault: string }
export interface PlanCriterionCheck { readonly criterion: string; readonly check: string }
/** All optional; present together on pipeline plans (validated at settle, Task 2). */
export interface PlanRecordFields {
  readonly changeShape?: typeof PLAN_CHANGE_SHAPES[number];
  readonly tier?: typeof PLAN_TIERS[number];
  readonly declaredScope?: readonly string[];      // directory prefixes, 1..64, each 1..256 chars, no "..", no leading "/"
  readonly nonGoals?: readonly string[];           // ≤32 × ≤1000
  readonly mechanicalPortions?: readonly string[]; // ≤32 × ≤1000
  readonly blockingQuestions?: readonly PlanBlockingQuestion[]; // ≤16; question ≤1000, default ≤1000
  readonly criterionChecks?: readonly PlanCriterionCheck[];     // ≤32; criterion ≤1000, check ≤512 no control chars
}
```

- `WorkflowPlanDraft` and `PlanRevision` both extend `PlanRecordFields`. `PlanRevision` additionally gains `rejectedNote?: string`.
- `work_items` columns: `pipeline_branch TEXT NULL`, `base_sha TEXT NULL` → `WorkItem.pipelineBranch: string | null`, `baseSha: string | null`.
- New table:

```sql
CREATE TABLE verify_attempts (
  verify_attempt_id TEXT PRIMARY KEY,
  node_id TEXT NOT NULL REFERENCES work_nodes(node_id),
  stage TEXT NOT NULL,
  attempt INTEGER NOT NULL,
  verify_run_id TEXT NULL,
  workspace_path TEXT NULL,
  state TEXT NOT NULL CHECK (state IN ('starting','running','green','failed','died','failed_to_start')),
  check_results_json TEXT NULL,
  detail TEXT NULL,
  created_at TEXT NOT NULL,
  ended_at TEXT NULL,
  UNIQUE(node_id, stage, attempt)
);
```

with contract type `VerifyAttempt` mirroring it (camelCase, `checkResults: readonly { criterion: string; check: string; passed: boolean }[] | null`).
- `plan_revisions` columns: `change_shape`, `tier`, `declared_scope_json`, `non_goals_json`, `mechanical_portions_json`, `blocking_questions_json`, `criterion_checks_json`, `rejected_note` — all NULL-able.
- Validators: server-side exact validation of the new fields inside the existing plan validators (`validate.ts` — extend `parseBoardConfirmPlan`-adjacent plan draft validation and the `WorkflowPlanDraft` validator used at settle); browser: extend `parseWorkflowPlan`'s projection (`parse.ts:286`) with the new optional fields (loose — ignore when absent). Do NOT touch enum tolerance buckets.
- v20 migration: `ALTER TABLE ADD COLUMN` × 10 + `CREATE TABLE verify_attempts`; bump `SCHEMA_VERSION` to 20. Migration test: open a v19 fixture DB, migrate, assert columns/table exist and existing rows survive with NULLs.

Steps: failing contract tests (round-trip a draft with all new fields; reject bad values: unknown changeShape, scope entry with `..`, >64 scope entries, control chars in check) → fail → implement → pass (`npm run verify:fast -- --base HEAD` inner loop; gate `npm run test:runtime`) → commit `feat: plan-record fields, pipeline branch columns, verify_attempts (schema v20)`.

### Task 7: Final approval, local merge, serial guard

**Files:** New `src/server/task-board/collaborators/merge-executor.ts`; modify `service.ts`, `schema.ts`, `board.ts`, `projects.ts`/`workflow.ts` (confirm serial guard); contract types; web `WorkItemDetail.tsx` + `client.ts` + `model`. Tests: merge unit; endpoints integration; web vitest.

**Behavior:**

- `GET /v1/work-items/:id/pipeline-summary` (human): `{ commits: {sha, subject}[], diffstat: string, filesTouched: string[], declaredScope, scopeOk, assumptions, midRunAssumptions, verify: VerifyAttempt[], criteria, criterionChecks }` — assembled read-only via the neutralized git runner (`log --format`, `diff --stat`, `diff --name-only` over `baseSha..pipeline_branch`) + DB. 409 when the item has no pipeline branch.
- `merge-executor.ts`: `mergePipelineBranch({ repoPath, branch, baseSha, git })` — assert the default branch's HEAD is an ancestor-consistent state (warn-only if HEAD moved past baseSha; merge proceeds), `git merge --no-ff --no-edit task/<id>` with neutralized flags on the default branch via a detached worktree-free sequence: run in the real repo (`git -C <repo> switch <default>` is intrusive — instead use `git -C <repo> merge` only if already on default; otherwise fail with `TASK_BOARD_PIPELINE_REPO_BUSY` telling the operator the repo isn't on its default branch). Conflict → `git merge --abort`, return conflict summary.
- `POST /v1/work-items/:id/approve-merge { version }` (human): requires `final_approval`; runs the merge; success → transition to `merged` (result records the merge commit sha); conflict → transition to `parked` with the conflict summary. `POST /v1/work-items/:id/reject-final { note, version }`: `final_approval → implementing`, note appended as a system handoff/message so the next engineer round sees it, node re-armed at `implementation`.
- **Serial guard:** at confirm of a pipeline plan, 409 `TASK_BOARD_PIPELINE_SERIAL_CONFLICT` if the project has another work item with a non-null `pipeline_branch` in states `implementing|verifying|final_approval|parked` (parked counts — resolve it first).
- **Web:** `final_approval` items render the pipeline summary (commits, diffstat, files vs scope with violations highlighted, assumptions with mid-run additions flagged — mid-run = assumptions appearing in handoff evidence but not the confirmed plan, computed server-side into `midRunAssumptions`), verify results and per-check outcomes, prose criteria; Approve & merge (confirm dialog) and Request changes (note dialog) controls.

Tests: merge unit against fixture repos (clean merge; conflict aborts leaving repo clean; not-on-default-branch error); integration approve→merged with commits on fixture main, reject-final→implementing re-armed; serial-guard 409. Web control tests. Commit `feat: final approval with local merge and serial pipeline guard`.
